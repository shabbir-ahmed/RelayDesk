# Production pilot

## Deploy to staging

1. Build the runtime and migration images from the same verified revision. Set `RELAYDESK_MODE=private` and configure the secret store and separate staging database as described in the [deployment guide](deployment.md). Confirm a recent restorable backup and record the time and previous healthy image digests.
2. Stop the previous web and worker when upgrading from Phase 3. Run the Phase 4 migration once. Start the new web service and then the worker. Drain and replace old workers before allowing signing rotation. Named users should sign in again after the upgrade.
3. Check `/api/health`, confirm a fresh worker heartbeat and an empty staging queue, then approve a staging receiver in Test. Provision a named owner and invite a second account. Verify that the two environments and unrelated workspaces keep their own keys and history.
4. Send a synthetic event from Test and confirm the receiver verified the signature over the exact raw body. Configure the receiver to return 422 for a known test event. Check that delivery history records the failure. Set the receiver to return 2xx and replay the same delivery. Check both attempts and confirm the event ID and body stayed the same. Exercise API key and signing rotation, and confirm a removed member's old cookie is rejected.
5. Run a representative burst against a healthy destination while an approved receiver times out or returns a retryable error. Record workload, worker count, and p95 time from queue eligibility to first claim for healthy events. Start with a target below 30 seconds at the agreed pilot workload. Stop a worker during a delivery and verify a replacement recovers the expired lease and completes queued work.
6. Rehearse rollback using the recorded images and restore a backup to an isolated PostgreSQL instance. Record time to recover and the newest usable data. Verify alerts reach the designated operator. Start production with a limited cohort after the staging checks pass.

## Credentials and retention

- In **Team**, named accounts can generate a recovery code by confirming their password. Save the single-use code in a password manager. Generating a new code replaces the old one. **Forgot your password?** uses the saved code to reset the password and revoke the account's sessions across workspaces. Generate a fresh code after resetting. This flow uses offline recovery codes and has no email reset. Workspace owners can remove members from **Team**, which immediately invalidates their workspace cookies, including after reinvitation.
- In **API keys**, rotate an existing key in the active environment. Save the replacement and update the producer. The old key works for 24 hours and can be revoked sooner in the same view. Workspace keys remain valid independently of who created them. If a departing member had access to a shared credential, rotate or revoke it.
- Rotate an endpoint's signing key from a trusted admin terminal with database access and `DESTINATION_SIGNING_KEY`: `npm run destination:rotate -- <workspace-slug> <test|live> <destination-id>`. Share the returned secret privately. During the 24-hour overlap, `X-RelayDesk-Signature` carries the old signature and `X-RelayDesk-Signature-Secondary` carries the new one. Receivers should verify both headers against configured keys using the existing signature format and accept a valid match. After the overlap, the primary header uses the new key and the secondary header disappears. Keep the signing root stable and separate across deployments.
- RelayDesk redacts private event payloads and canonical request bodies after 30 days once the event has no pending or processing deliveries. Manual replay expires at 30 days. Delivery and attempt metadata, audit history, and idempotency receipts remain available for the pilot. Backups can contain payloads until their separate retention window ends.
- Initial daily limits per workspace are 100 events and 500 deliveries in Test, and 1,000 events and 5,000 deliveries in Live. Each fan-out destination and manual replay counts toward the delivery limit. Idempotent submissions and automatic retries incur no additional delivery charge. Only one attempt per destination runs at a time across workers. Duplicate deliveries can occur after timeouts or worker failures. Use the stable event or delivery ID to deduplicate and process idempotently.

## Monitoring

Configure the Prometheus job `relaydesk` to scrape `/api/ops/metrics` over the internal ingress path or HTTPS using `Authorization: Bearer <OPS_METRICS_TOKEN>` from a secret file. Load [the alert rules](../ops/prometheus-alerts.yml) and route them through the operator's configured alerting service. Set an owner for each staging and production alert route. Combine the worker and queue alerts with the host's alerts for web availability, database utilization, and backup failure. Keep request bodies and authorization headers out of platform logs.

- **Stale worker or expired leases.** Check database access and worker logs, and confirm that the worker is running against the right database and mode. Restart it if needed. A lease expires after 30 seconds and the worker can requeue it. Check the attempt history and allow for duplicates at the receiver.
- **Queue lag or delivery failure.** Check backlog, recent retries, and the workspace's failed deliveries. Confirm that receivers can respond and validate signatures. Keep the per-destination limit in place. Increase the number of worker replicas only after checking database connection headroom and confirming the backlog spans multiple destinations.
- **Database outage or bad deployment.** Pause ingestion and the worker if successful deliveries or data integrity are in doubt. Restore managed PostgreSQL to a separate instance at the selected recovery point. Verify migrations, tenant isolation, queue state, and signed delivery before changing the database connection. Reconcile deliveries accepted or sent after the restore point with producers and receivers.
- **Application rollback.** Restore the last compatible web and worker image pair. Leave additive migrations in place for a Phase 4 release rehearsal before Phase 4 credentials or retention changes are active. Once Phase 4 has rotated or expired credentials, use a compatible Phase 4 build or a forward fix. A Phase 3 process does not enforce the new credential states and cannot sign with the newer keys.
